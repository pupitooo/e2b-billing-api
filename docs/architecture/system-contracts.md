# System contracts

Changes to financial, transport, or lifecycle requirements must update this
register and the linked detailed contract together. Keep proposals separate;
resolve conflicts with the assignment before adopting or implementing them.

| Contract | Required behavior and detail | Basis |
| --- | --- | --- |
| Durable usage and retries | The batch envelope contains only `events`, with no batch identity. Preserve increments under source-wide `(source, event_id)` identities across customers, sandboxes, processes, and restarts. Acknowledge committed input; unchanged retries preserve receipt time, changed content conflicts, and the sender retains unacknowledged input. [Event contract](usage-to-invoice.md#3-usage-events-what-was-consumed). | Assignment delivery; system identity and inbox policies. |
| API and worker lifecycle | Separate processes and containers, independent restarts, shared PostgreSQL capacity. Each process constructs one PostgreSQL store with shared connection, clock, and rollback settings. The API requires the complete store at startup and always registers all implemented endpoints. [Runtime boundaries](submission-overview.md#runtime-boundaries), [option C](../brainstorming/architecture-options.md#why-option-c-was-selected). | System architecture. |
| Historical pricing | Apply consumption-time overrides or defaults with finite, explicit starts. Preserve seed prices and dates; receipts fit one price version and UTC month. [Pricing](accounting-rules.md#historical-prices-and-groups). | Assignment prices; system segmentation policy. |
| Generated resource IDs and command retries | Billing generates price IDs and derives readable new subscription IDs as `subscription/<customer_id>/<addon_name>` with each component percent-encoded. Prices, add-ons, credit grants, and spend-limit changes require JSON `idempotency_key`; all four commands store their keys and results in `api_idempotency_operations` in the same transaction as their financial effects. Caller keys never become internal resource IDs. Missing or invalid keys return `422`; duplicate fields or wrong types return `400`; changed content conflicts. Existing IDs and financial history remain unchanged. [Command retries](../guides/api-reference.md#command-retries). | System API identity policy. |
| Accounting resource IDs | New rated groups use `grp_1`, `grp_2`, etc.; new credit ledger entries use `crd_1`, `crd_2`, etc. Each namespace has a persistent, noncycling PostgreSQL sequence starting at one. Allocation is safe across API and worker instances without a collision lookup. Rollback can leave gaps; existing IDs, references and invoices are preserved. [Identity rules](accounting-rules.md#accounting-resource-identities). | System storage identity policy. |
| Price insertion | `effective_from` is a required `YYYY-MM-DD` date, stored at midnight UTC. New dates must be today or later according to the server clock after the catalog lock. Today is allowed only when rated history is preserved. Past dates return `422`; history conflicts return `409`; unchanged retries retain the original price. [Insertion contract](accounting-rules.md#price-insertion-contract). | System activation policy. |
| Credit audit time | Grant requests and responses contain no `recorded_at`. The backend writes its UTC clock to the ledger and command history once; retries preserve that audit instant. [Credit contract](accounting-rules.md#credit-audit-time-and-add-on-purchase-dates). | System audit policy. |
| Add-on purchase date | `purchased_at` is a required `YYYY-MM-DD` date, stored at midnight UTC and returned as a date. Open historical months and future dates are allowed; new purchases in or before a closing or closed month conflict. [Purchase contract](accounting-rules.md#credit-audit-time-and-add-on-purchase-dates). | System purchase policy. |
| Catalog recovery | Provision dated prices before metering. Missing prices quarantine without financial effects and report P0; repair through controlled SQL, then explicitly release. [Recovery contract](accounting-rules.md#catalog-provisioning-and-p0-recovery). | System provisioning policy. |
| Exact money and credit | Allocate exact ticks before rounding; credit pays usage only and later grants do not rewrite allocations. [Money and credit](accounting-rules.md#exact-money-and-credit). | Assignment credit; system precision/order. |
| Invoice presentation | Round cumulative groups half-up; displayed credit is rounded gross minus net. Preserve exact audit values and assignment totals. [Presentation](accounting-rules.md#rounding-and-invoice-presentation). | Assignment cents/examples; system rounding. |
| Fixed monthly periods | Whole UTC calendar months, one immutable invoice per customer/month after month end; retries retain number and snapshot. [Months](accounting-rules.md#fixed-calendar-month-contract). | Assignment periods; system closing guarantees. |
| Spend limits and add-ons | Compare original-month gross usage before credit, excluding add-ons; account beyond the limit. Charge the full add-on price from its purchase month. [Rules](accounting-rules.md#utc-months-limits-add-ons-and-late-usage). | Assignment rules. |
| Late usage | Preserve consumption-month prices, limits, and audit; route closed/skipped-month usage to an eligible month after the latest closure and at or after receipt. Issued invoices never reopen. [Late usage](accounting-rules.md#utc-months-limits-add-ons-and-late-usage). | Assignment example; system routing policy. |
| Atomic accounting and closing | Serialize customer financial writes; commit each receipt with its financial effects. Close already processed groups under the account lock without draining or blocking on pending/errors. First closing cannot skip earlier usage; later new invoices require the previous month closed. Publish closure, frozen groups, snapshot, and number atomically. [Closing contract](accounting-rules.md#transaction-and-closing-contract). | System transaction policy. |
| Supported timestamps | After UTC conversion, years 1000 through 9999 with at most microsecond precision. [Event validation](usage-to-invoice.md#3-usage-events-what-was-consumed). | System parsing boundaries. |

Automatic invoice scheduling/delivery, external invoice references, configurable
price denominators, and alternative catalog locking remain proposals.
